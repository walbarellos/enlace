# 02.04 — ADR-003: IMPLEMENTAÇÃO DE MOTOR DE POLÍTICAS CENTRALIZADO (RBAC + ABAC)

> **Documento:** 02.04  
> **Status:** Aprovado  
> **Data:** 25 de Setembro de 2026  
> **Decisores:** Arquiteto de Segurança, Tech Lead  

---

## 1. Contexto do Problema

Vulnerabilidades de controle de acesso quebrado (*Broken Object Level Authorization - BOLA* e *Broken Function Level Authorization - BFLA*) representam o vetor número 1 de invasões e vazamento de dados em APIs (OWASP API Security Top 10). Em plataformas com modelos de permissão complexos (maioridade, verificação em níveis, pseudonimização, titularidade de mídias privadas e bloqueios mútuos), espalhar condicionais `if` nos controladores HTTP gera brechas fatais de segurança e dificulta testes de conformidade.

## 2. Decisão Arquitetural

Decidiu-se pela criação de um componente desacoplado denominado **Policy Engine**, responsável por avaliar qualquer autorização de forma declarativa e determinística antes da execução de um caso de uso.

- **Combinação RBAC + ABAC:** O motor avalia o papel do ator (*Role*), os atributos do sujeito (*Subject*: idade calculada, nível de verificação, score de risco), os atributos do recurso (*Resource*: preço, visibilidade, proprietário) e o contexto do ambiente (*Context*: bloqueio mútuo, desafio bot).
- **Sem Efeitos Colaterais:** Toda classe de política (`AgePolicy`, `ContentAccessPolicy`, `PurchasePolicy`, etc.) é uma função pura e síncrona que retorna exclusivamente um objeto `PolicyDecision { allowed: boolean, reason?: string }`.

```typescript
export class ContentAccessPolicy {
  public static canAccess(
    subject: SubjectContext,
    resource: ContentResourceContext,
    entitlements: EntitlementSnapshot
  ): PolicyDecision {
    if (resource.tier === AccessTier.PUBLIC) {
      return PolicyDecision.allow();
    }
    if (subject.accountId === resource.ownerId) {
      return PolicyDecision.allow();
    }
    if (entitlements.hasValidEntitlementFor(resource.id)) {
      return PolicyDecision.allow();
    }
    return PolicyDecision.deny("RECURSO_PAGO_SEM_ENTITLEMENT_ATIVO");
  }
}
```

## 3. Consequências e Trade-Offs

### Consequências Positivas:
- **Testabilidade Total:** Políticas podem ser cobertas por matrizes exaustivas de testes unitários em microssegundos, testando todas as combinações de permissões sem necessidade de mocks ou banco de dados.
- **Auditoria Simplificada:** Em caso de investigação de conformidade ou perícia de segurança, as regras de autorização estão centralizadas em arquivos únicos legíveis, e não espalhadas por centenas de métodos.
- **Eliminação de BOLA/IDOR:** Os controladores nunca autorizam acesso a objetos baseado apenas no ID passado na URL; a política valida a posse e o entitlement.

### Consequências Negativas:
- Exige que os casos de uso carreguem previamente os snapshots de contexto necessários para a avaliação da política.
