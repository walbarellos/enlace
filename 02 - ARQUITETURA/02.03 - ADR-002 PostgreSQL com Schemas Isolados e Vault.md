# 02.03 — ADR-002: POSTGRESQL COM SCHEMAS ISOLADOS E COFRE CIVIL CRIPTOGRAFADO

> **Documento:** 02.03  
> **Status:** Aprovado  
> **Data:** 25 de Setembro de 2026  
> **Decisores:** Arquiteto de Software, Especialista em Cibersegurança, DPO/LGPD  

---

## 1. Contexto do Problema

A plataforma trata dados de alta sensibilidade pessoal e jurídica: de um lado, anúncios públicos com fotos artísticas e nomes fantasia; de outro lado, documentos civis (RG/CNH), CPFs de batismo, fotos biométricas de vivacidade e contas bancárias de acompanhantes.

Se um único ataque de injeção SQL ou falha de autorização na API pública pudesse ler a mesma tabela onde residem os nomes civis, o impacto de doxxing seria catastrófico. Por outro lado, manter múltiplos clusters de banco de dados separados geraria custos e complexidade excessivos no lançamento regional (Acre).

## 2. Decisão Arquitetural

Decidiu-se pela unificação em um único cluster gerenciado **PostgreSQL 16+** com **Segregação de Esquemas e Row-Level Security (RLS)**:

1. **Esquema `public`:**
   - Armazena todas as tabelas operacionais da vitrine (perfis artísticos, catálogo, mídias públicas, avaliações sob pseudônimo, ordens de serviço e splits).
2. **Esquema `vault_civil`:**
   - Esquema isolado contendo exclusivamente as tabelas de identificação civil legal (`identities`, `biometrics`, `kyc_documents`).
   - Dados gravados em colunas binárias (`bytea`) com criptografia de envelope AES-256-GCM com chaves gerenciadas externamente (KMS).
3. **Segregação Estrita de Credenciais no Banco:**
   - A aplicação web pública conecta-se com o usuário `enlace_app_user`, que tem permissões apenas no esquema `public`. O comando `REVOKE ALL ON SCHEMA vault_civil FROM enlace_app_user;` é aplicado na inicialização do banco.
   - Apenas o worker especializado em KYC (`enlace_vault_worker_user`) possui credenciais para ler e escrever no esquema `vault_civil`.

```text
               APLICAÇÃO WEB / API PÚBLICA             WORKER ASSÍNCRONO DE KYC
                            │                                     │
                     (enlace_app_user)                (enlace_vault_worker_user)
                            │                                     │
                            ▼                                     ▼
                ┌───────────────────────┐             ┌───────────────────────┐
                │    ESQUEMA: public    │             │  ESQUEMA: vault_civil │
                ├───────────────────────┤             ├───────────────────────┤
                │ • provider_profiles   │             │ • identities (AES-256)│
                │ • client_profiles     │             │ • documents (Bytea)   │
                │ • orders & splits     │             │ • biometrics (Hash)   │
                │ • reviews             │             │ • pix_keys (AES-256)  │
                └───────────────────────┘             └───────────────────────┘
```

## 3. Consequências e Trade-Offs

### Consequências Positivas:
- **Imunidade contra Vazamento por SQLi no Frontend:** Mesmo na hipótese remota de um invasor explorar uma vulnerabilidade de SQL Injection na busca do catálogo, a conexão do banco não possui permissão de leitura sobre o esquema `vault_civil`.
- **Eficiência de Recursos:** Um único cluster PostgreSQL (com réplica de leitura) atende a toda a aplicação, reduzindo custos de banco gerenciado.
- **Conformidade com a LGPD (Art. 11):** Salvaguarda técnica formal para dados pessoais altamente sensíveis.

### Consequências Negativas:
- Consultas analíticas administrativas que exijam cruzar dados de pagamento com documentos civis não podem fazer `JOIN` direto na camada pública, exigindo reconciliação assíncrona por workers autorizados.
