## 1. Princípios da Arquitetura Hexagonal (Ports & Adapters)

A regra de dependência inviolável na Plataforma Enlace estabelece que:

> **O Domínio nunca conhece a Infraestrutura.**
> As regras de negócio dependem exclusivamente de interfaces abstratas (Ports), enquanto os adaptadores concretos (bancos de dados, gateways de pagamento, APIs externas) implementam essas portas a partir da camada externa.

```
       [ HTTP / Inbound Controller ]
                   │
                   ▼ (Invoca Use Case)
       [ Application Service / Use Case ]
                   │
      ┌────────────┴────────────┐
      ▼                         ▼
[ Domain Entities & Policies ] [ Secondary Port (Interface) ]
                                        ▲
                                        │ (Implementa)
                               [ Database / Redis Adapter ]
```

## 2. Tratamento de Erros com Monad `Result<T, E>`

Para garantir tipagem estrita e evitar o uso indiscriminado de `try/catch` para fluxo de controle de negócio, todos os Use Cases retornam instâncias da classe canônica `Result<T, E>`:

```typescript
// Exemplo canônico de uso
const result = await RegisterAccountUseCase.execute(dto);

if (!result.isSuccess) {
  // Erro tratado como valor tipado
  return reply.status(400).send({ error: result.error });
}

// Valor extraído com garantia de segurança
const data = result.value;
```

### 2.1. Tabela de Mapeamento de Erros para Códigos HTTP

| Cenário de Negócio | Monad Error Code | HTTP Status |
| :--- | :--- | :--- |
| Validação de esquema falhou | `VALIDATION_ERROR` | 400 Bad Request |
| Menor de 18 anos detectado | `AGE_UNDER_18_PROHIBITED` | 403 Forbidden |
| Documento em blacklist | `DOCUMENT_BLACKLISTED` | 403 Forbidden |
| Credenciais inválidas | `INVALID_CREDENTIALS` | 401 Unauthorized |
| Mídia bloqueada por paywall | `ENTITLEMENT_REQUIRED` | 402 Payment Required |
| Recurso não localizado | `RESOURCE_NOT_FOUND` | 404 Not Found |
| Conflito de integridade / duplicidade | `DUPLICATE_ENTITY` | 409 Conflict |

## 3. Isolamento Transacional de Banco de Dados

1. **Uso de Transações Explícitas (`BEGIN` / `COMMIT` / `ROLLBACK`):**
   * Toda operação que afete mais de uma tabela (ex: criação de conta + perfil, checkout Pix + outbox, liquidação + concessão de direito) é executada compulsoriamente dentro de bloco transacional com liberação garantida do cliente no bloco `finally`.
2. **Prevenção de Deadlocks:**
   * Bloqueios de linha para concorrência de ordens utilizam compulsoriamente a cláusula `FOR UPDATE`.
