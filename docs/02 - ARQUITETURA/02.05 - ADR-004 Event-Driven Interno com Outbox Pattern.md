# 02.05 — ADR-004: COMUNICAÇÃO EVENT-DRIVEN INTERNA COM TRANSACTIONAL OUTBOX

> **Documento:** 02.05  
> **Status:** Aprovado  
> **Data:** 25 de Setembro de 2026  
> **Decisores:** Arquiteto de Software, Engenheiro de Dados  

---

## 1. Contexto do Problema

Mesmo operando dentro de um monólito modular, acoplar chamadas síncronas entre módulos diferentes cria o clássico problema de efeito dominó (*cascade failures*): se a notificação de e-mail falhar, a transação financeira é desfeita? Se o processador de vídeo travar, o cadastro da acompanhante é abortado?

Além disso, utilizar um broker de mensagens externo distribuído (como Kafka ou RabbitMQ) no início do projeto adicionaria uma camada complexa de manutenção e infraestrutura, desproporcional ao volume inicial do piloto (Acre).

## 2. Decisão Arquitetural

Decidiu-se pela implementação de um **Barramento de Eventos de Domínio Interno (In-Process Event Bus)** combinado com o **Padrão Transactional Outbox**:

1. **Barramento em Memória Assíncrono:** Os módulos publicam eventos de domínio puros (`DomainEvent`). Handlers dentro do mesmo monólito assinam esses eventos e executam suas ações sem bloquear o fluxo HTTP do cliente.
2. **Transactional Outbox para Operações Financeiras:**
   - Para eventos críticos de receita (ex: `PaymentConfirmedEvent`), o evento é gravado na tabela `public.outbox_events` **dentro da mesma transação SQL** que confirma o pagamento.
   - Um worker leve em background consome a tabela e entrega o evento com garantia de entrega *At-Least-Once*, tolerando quedas ou reinicializações do processo.
3. **Idempotência Obrigatória:** Todos os handlers implementam verificação de chave de idempotência para suportar reentregas sem efeitos duplicados.

## 3. Consequências e Trade-Offs

### Consequências Positivas:
- **Resiliência Transacional:** Zero risco de receber um pagamento Pix e perder a concessão do acesso ou o agendamento de esteganografia.
- **Simplicidade de Infraestrutura:** Elimina a necessidade de operar um cluster Kafka ou RabbitMQ no lançamento, rodando integralmente no PostgreSQL e Redis.
- **Portabilidade para o Futuro:** Se o volume justificar extração de serviços no futuro, basta alterar a implementação do barramento para despachar para um broker externo, sem alterar as classes de domínio.

### Consequências Negativas:
- Exige polling de baixa latência ou *Listen/Notify* do PostgreSQL para processamento dos registros da tabela Outbox.
